Mumbai → Oman disaster recovery scenarios

Prepared by CloudZ13 (DB services) · AWS passive DR cost calculator →

Each server group has a load balancer, 3 Tomcat servers, a production DB and a DB replica. Mumbai is the primary site. Oman is the DR site with a copy of every server at 20% capacity. Only the Oman DB is kept in sync (Oracle Standard Edition log shipping). Everything else in Oman is a stopped copy of Mumbai. In every diagram, Mumbai is on the left and Oman is on the right.

Design points to settle

Architecture

  • Server count. The listed roles are 6 per site (LB, 3 Tomcat, DB, DB replica). Confirm what the 7th server is, for example a web/proxy tier, a jump host or a monitoring/backup server.
  • Single load balancer. One LB per site is a single point of failure. A failed Mumbai LB forces a full DR failover. An LB pair (or a cloud LB) avoids this.
  • DNS TTL. Keep the record TTL low (60–300 s) so the switch to Oman takes effect quickly. Clients and resolvers that cache longer will lag behind.
  • App DB connection. Each site's Tomcats should point to a local DB alias (DNS name or VIP). The same build then works at both sites, and a local DB switch only moves the alias.

Data & operations

  • RPO. SE2 log shipping is asynchronous. A disaster loses whatever redo has not reached Oman yet. Ship logs often enough to meet the RPO target and alert on lag.
  • Split-brain. Before opening the Oman DB, fence Mumbai: power it off or block it so it can never come back as a second primary.
  • 20% capacity. Decide in advance which features to disable on DR (reports, batch jobs, exports) and how to scale Oman up if the outage runs long.
  • Drills. Rehearse failover and switchback at least twice a year, using runbooks with named owners and a timed checklist.
